**用到的几个词**：
- PPE：芯片里固定功能的交换和转发硬件。
- EDMA：在 PPE 和 CPU 之间搬报文的硬件，用环形队列（下面叫"环"）交接。
- 前置头：EDMA 放在每个报文前面的 32 字节，里面有口号。
- UNIPHY：把 MAC 的信号变成串行信号送给 PHY 芯片的硬件，Linux 里叫 PCS。
- 口的发送开关：PPE 里每个口有一位，管 PPE 往这个口送不送报文。
- 广播域：PPE 里叫 VSI。地址表按广播域分开查；不认识的单播、组播、广播，发给这个广播域登记的口。

## 一、要你定的事

### 第 1 件：设备树里怎样描述这块硬件

**定了**：做法甲。你的原话："选甲, 另外目前我只有ipq8设备没有6, 所以6先不做, 这个暂时搁置, 等我有ipq6的设备再说."

**现在是什么样**（`ipq8074-ess.dtsi`，SoC 的设备树）：
- 两个并列的节点：`ppe@3a000000`（寄存器 0x900000 长）和 `edma@3ab00000`（寄存器 0xb0000 长）。EDMA 的地址就是 PPE 的地址加 0xb00000。
- 两个节点的名字都用了 `qualcomm,` 这个前缀。
- EDMA 列 4 个中断，不带名字，驱动按次序取。
- PPE 节点上列 33 个时钟、7 条复位线，六个口的时钟和复位线都挂在这一个节点上，靠名字 `port1_rx`、`nss_port1_rst` 区分。
- 口写成 `ports/port@N`，是 DSA 的写法，其中 `port@0` 是通向 EDMA 的 CPU 口。口的节点由每块板子自己写。

**做法甲：照已经进 Linux 的 IPQ9574 的写法。**

```text
ethernet-switch@3a000000        一个节点，寄存器从 PPE 开头到 EDMA 结尾，共 0xbb0000 长
│  名字 "qcom,ipq8074-ppe"
│  整块 PPE 的时钟、整块 PPE 的复位线
├─ ethernet-dma                 EDMA，子节点，没有自己的寄存器
│     EDMA 的时钟、EDMA 的复位线
│     中断带名字：txcmpl_0 … txcmpl_7、rxfill_0 … rxfill_7、rxdesc_0 … rxdesc_15、misc
└─ ethernet-ports
      ethernet-port@1 … @6      每个口自己的时钟、自己的复位线
                                 板子再加：名字、PHY、PCS、连接方式、MAC 地址
```

- 口的节点里，芯片固定的东西（口号、时钟、复位线）写在 SoC 的设备树里，板子只写板子上才有的东西。
- 中断按名字取。IPQ807x 的 33 个中断用你给的那张表，33 个号都是测到的（出处：用户给的，以前在硬件上直接测到）：
  - 发送完成环 n：SPI 352 − n，n 从 0 到 7。
  - 接收填充环 n：SPI 360 − n，n 从 0 到 7。
  - 接收描述环 n：SPI 376 − n，n 从 0 到 15。
  - 杂项：SPI 344。
  - 我核了一处：现在设备树里的三个环中断是 345、353、361，正好是这张表里的发送完成环 7、接收填充环 7、接收描述环 15，和现在驱动用的环号对得上。

**做法乙（没有选）**：保留现在的两个节点，只去掉 `port@0` 这个 CPU 口，把名字前缀改掉，中断还是 4 个不带名字。

**做法甲的依据**：
- 已经进 Linux 的绑定 `references/upstream/linux/Documentation/devicetree/bindings/net/qcom,ipq9574-ppe.yaml`：第 243 行节点叫 `ethernet-switch@3a000000`，第 271 行 EDMA 是子节点 `ethernet-dma`，第 409 行口在 `ethernet-ports` 下面。
- `关键设计.md` 第 25 条：命名和文件组织照上游的习惯，设备树不针对一块板子。
- 这块芯片的 EDMA 的寄存器就在 PPE 的地址范围后面（现在的设备树 `ipq8074-ess.dtsi` 第 90 行和第 116 行）。

**IPQ60xx 搁置以后跟着来的事**（这一段是我按"6先不做"推出来的，不是你的原话）：
- `ipq6018-ess.dtsi` 不改，IPQ60xx 的板子继续用旧的描述和旧的驱动。
- 所以旧驱动的文件、接旧驱动的补丁、IPQ60xx 的内核配置都要留着，阶段 1 里删不掉。

### 第 2 件：每个口的名字和 MAC 地址

**定了**：名字用做法甲；地址用做法甲，不再是暂定。你的原话："地址这一件定了，不再是暂定：每个口读自己节点里的地址，没有就随机生成。"

**地址的依据**（你给的，原厂的行为）：这块板子原厂是五个有线口共用一个地址。来路有三处，前两处是你核过的，第三处是读原厂 U-Boot 的程序读出来的：
- 出厂数据分区里存着一个有线基准地址；
- 原厂 U-Boot 的环境变量 `ethaddr` 等于这个基准地址；
- 原厂 U-Boot 给各个以太网接口用同一个基准地址，没有按口加一。

现在的板级文件里五个口读的都是 `ethaddr`，所以照现在的板级文件做，五个口地址相同，就是原厂的行为。
原厂系统启动以后会不会再改各个口的地址，还没有核完。
地址的具体数值不写进任何文件。

**现在是什么样**：
- 名字：板级文件里每个口写 `label`（例如 `lan1`、`wan`），DSA 用它当网口的名字。48 个带口的设备树文件里，3 个没有写 `label`。
- 地址：WXR-5950AX12 的五个口都从同一处存储读地址，五个口地址相同（`ipq8074-wxr-5950ax12.dts` 第 289、299、309、320、331 行）。48 个文件里有 28 个，口的节点里没有写地址；这些口现在沿用 EDMA 那个网口的地址，那个地址来自设备树里别处，都没有就随机生成一个（`qca_edma.c` 第 1231 到 1258 行、第 1302 到 1306 行）。有些板子，OpenWrt 的启动脚本之后还会再设一遍（`ipq807x/base-files/etc/board.d/02_network` 第 89 行起的 `ipq807x_setup_macs`）；WXR-5950AX12 不在其中。

**不管怎样定，你都会看到的两处变化**：
- `eth0` 没有了。它是 EDMA 那个共用的网口，一体驱动里没有它。
- 第一步的镜像里网口不能收发，上机时 ssh 用不了，只能走串口（`脚本说明.md` 里的 `serial-command.py`）。

**名字的做法甲**：驱动读 `label`，注册时就用这个名字。没有 `label` 的口用内核默认的 `eth0`、`eth1`。
依据：`关键设计.md` 第 14 条；IPQ9574 的 0339 号补丁就是这样做的，它在上游的 OpenWrt 里；Linux 的绑定 `ethernet-controller.yaml` 第 16 行定义了 `label`。
一处要照实说：在 Linux 自己的源码里，我没有找到不用 DSA 而用 `label` 给网口起名的驱动。有先例的是上游的 OpenWrt。

**地址，两种做法**：
- 做法甲（定了）：每个口只读自己节点里的地址，没有就各自随机生成。IPQ9574 的 0332 号补丁是这样做的。

## 二、骨架（管整个阶段 1）

### 分哪几个文件

目录是 `drivers/net/ethernet/qualcomm/ipq807x/`，整个目录编成一个模块 `ipq807x-eth`。

| 文件 | 管什么 | 第一步有没有内容 |
|---|---|---|
| `ppe.c` | 驱动的入口：认设备、开时钟、复位、建寄存器映射、按次序调用各文件的开机配置、建口；退出时收拾 | 有 |
| `ppe.h` | 整个驱动共用的数据结构 | 有 |
| `ppe_regs.h` | PPE 的寄存器 | 有 |
| `ppe_config.c` | PPE 的开机配置：缓冲区、队列、调度器、送 CPU 的队列、各口的默认值、各口互相隔开、生成树协议报文的规则 | 有 |
| `ppe_port.c` | 每个口硬件的一面：MAC、口的时钟和复位、phylink 要的 MAC 操作、计数器 | 有：取并打开口的时钟、取复位线、MAC 的共同设置 |
| `ppe_netdev.c` | 每个口 Linux 的一面：分配和注册网口、网口的操作 | 有 |
| `edma.c` | EDMA 硬件：复位、开机配置、环的分配、中断 | 有复位和开机配置 |
| `edma_regs.h` | EDMA 的寄存器 | 有 |
| `edma_rx.c` | 收包 | 没有 |
| `edma_tx.c` | 发包 | 没有 |
| `ppe_ethtool.c` | ethtool（查看和设置网口的命令）要的操作 | 没有 |
| `ppe_devlink.c` | devlink 的端口和健康报告 | 没有 |

和 IPQ9574 的驱动比：`ppe.c`、`ppe_regs.h`、`ppe_config.c`、`ppe_port.c`、`edma.c`、`edma_rx.c`、`edma_tx.c` 这七个名字和它管的事是一样的。
不一样的一处：IPQ9574 把网口放在 `edma_port.c`。我放在 `ppe_netdev.c`，理由是网口是"口"的一面，而 EDMA 是所有口共用的，不属于哪一个口。

### 主要的数据结构

| 结构 | 有几份 | 放什么 |
|---|---|---|
| `struct ppe_soc_data` | 每种芯片一份，写死在驱动里。现在只有 IPQ807x 一份 | 口的数目、千兆 MAC 的数目、哪几个口有万兆 MAC、几张表的步长、缓冲区和队列的数值、两张调度时间表、EDMA 几组寄存器的位置、每种环的总数、主机用哪几个环、最短帧长、杂项中断的掩码 |
| `struct ppe_device` | 整个驱动一份 | 设备、寄存器映射、指向芯片数据、整块 PPE 的时钟和复位线、配置锁、口的数组、EDMA 的状态 |
| `struct ppe_port` | 每个口一份，就是网口的私有数据 | 口号、网口、设备树节点、指回 `ppe_device`、口的三个时钟和复位线、网口注册过没有。后面的步骤再加：phylink、PCS、计数器 |
| `struct edma` | 一份，放在 `ppe_device` 里面 | EDMA 的两个时钟和复位线。后面的步骤再加：环、中断、收发的轮询 |
| `struct edma_ring` | 每个环一份，后面的步骤才有 | 描述符的内存、长度、环号 |

三处和现在的驱动不一样：
- 现在 PPE 和 EDMA 各有一份芯片数据（`qca_ppe_main.c` 第 1879 到 1894 行，`qca_edma.c` 第 1389 到 1398 行），新驱动合成一份。
- 现在 PPE 和 EDMA 各有一份寄存器映射，新驱动只有一份，EDMA 的寄存器是 PPE 基址加 0xb00000。IPQ9574 的驱动也是一份。
- 一个口只有一个结构。IPQ9574 一个口有两个结构，分在两个文件里。

芯片数据仍然单独做成一个结构，虽然现在只有一份：审稿人要求每种芯片的参数放在驱动里，不放在设备树里；IPQ60xx 有硬件以后加第二份。

芯片数据那一行列的是整个阶段 1 要放的东西；第一步的代码里只放了第一步用到的那些，"哪几个口有万兆 MAC""最短帧长""杂项中断的掩码"到用的那一步再加。

"主机用哪几个环"写在芯片数据里，不写在设备树里。候选值照现在的：发包环 23、发完环 7、空缓冲区环 7、收包环 15。这几个数出自 `qca_edma.c` 第 1389 到 1398 行；`references/qosmio/openwrt-ipq` 里照厂商写法的设备树（`ipq8074-ess.dtsi` 的 `qcom,edma` 节点）也是这几个数。以后要多用环，只改驱动里的这张表。

### 哪里加锁

| 锁 | 护什么 | 谁拿 | 第一步用不用 |
|---|---|---|---|
| 配置锁，互斥锁，在 `ppe_device` 里 | PPE 里要连着写几个字才生效的表项，和"读出来、改几位、写回去"的寄存器 | 能睡觉的配置路径：加载、以后的 phylink 回调、以后的 switchdev | 用 |
| 寄存器映射自带的锁 | 一次读或写一个寄存器 | 内核自己拿。内存映射的寄存器映射自带一把自旋锁（`drivers/base/regmap/regmap-mmio.c` 第 398 行） | 用 |
| 发包环的锁，自旋锁，每个发包环一把 | 几个口的网口往同一个发包环里放报文 | 发送函数 | 不用 |
| 计数器的锁，自旋锁 | 口的计数器。内核读计数器时不许睡觉 | 读计数器的函数、定时累加的任务 | 不用 |
| 内核的网络配置锁 | 网口的注册、打开、关闭 | 内核自己拿 | 用 |

收包和处理"发完"不加锁：内核保证同一个轮询同一时间只有一处在跑。
收发路径不拿配置锁。
现在的驱动给地址表单独备了一把自旋锁。第一步里地址表只在加载时清空一次，在配置锁里面做，不另备锁；地址表在运行时有人改是阶段 3 的事。

### 一个报文的内存每一段归谁

**收包的一页内存**，从前到后四段：

```text
| 给 Linux 留的空位 | 32 字节前置头 | 报文 | 剩下的空位和 skb 的尾部信息 |
```

| 时间 | 整页归谁 | 谁可以写哪一段 |
|---|---|---|
| 驱动从页池里拿到 | 驱动 | 驱动可以写任何一段 |
| 驱动把它登记进空缓冲区环、写了位置寄存器以后 | 硬件 | 硬件只写"前置头"和"报文"两段。驱动一段都不碰 |
| 硬件在收包环里交回来以后 | 驱动 | 驱动读前置头，取口号 |
| 驱动把它做成 skb 交给 Linux 以后 | Linux | 驱动不再碰。skb 释放时这一页回到页池 |

驱动自己记的"哪个槽位放的是哪一页"的表，一直归驱动。

**发包的 skb**，从前到后三段：

```text
| 前面的空位，至少 32 字节 | 驱动压进去的 32 字节前置头 | 报文 |
```

| 时间 | 归谁 | 说明 |
|---|---|---|
| Linux 调发送函数 | 驱动 | 驱动往前面的空位里写前置头以前，先确认这块内存只有自己在用 |
| 驱动写了描述符和位置寄存器以后 | 硬件 | 硬件读前置头和报文。驱动留着 skb 的指针，不改不放 |
| 硬件在发完环里报告以后 | 驱动 | 驱动解除映射，释放 skb |

**环的描述符内存**：从分配到释放一直归驱动；两个位置寄存器之间的那些格子，硬件在读写。

收发是后面的步骤，这里只定归属，细节到那一步再写。

- 网口分成"分配"和"注册"两步，中间隔着时钟、复位和开机配置：口的时钟要在 PPE 复位以前打开（照现在的次序），而时钟记在 `ppe_port` 里，`ppe_port` 是网口的私有数据，所以网口要先分配；注册放在最后，是为了硬件配好以前别人看不到这些口。
- EDMA 的几个函数不拿配置锁，因为它们写的都是单个寄存器，而且只在加载和卸载时跑。
- 第一步的网口不提供"打开""关闭"两个操作，内核允许不提供。`ip link set lan1 up`（把口打开的命令）会成功，但显示没有连线。
- `ppe_netdev_xmit` 第一步就要有：没有它，有程序绕过队列直接往这个口发报文时，内核会去调一个不存在的函数。

**设备树里和代码对应的名字**：
- `ethernet-switch` 节点：复位线叫 `ppe`；时钟不按名字取，节点上列的全部打开。
- `ethernet-dma` 子节点：时钟叫 `sys`、`apb`（和 IPQ9574 的绑定同名），复位线叫 `edma`。
- 每个口的节点：时钟叫 `mac`、`rx`、`tx`（和 IPQ9574 的绑定同名），复位线只有一条，不带名字。

**内核选项和包**：内核选项叫 `CONFIG_QCOM_IPQ807X_ETH`，包叫 `kmod-ipq807x-eth`，开机时早早加载。

### 4.1　查清的第一处：认识的单播会不会不经过 CPU 直接转发

**结论**：照现在驱动写进去的值，会（推论）。新驱动改成每个口一个自己的广播域，就不会（推论）。
上机（E-0001）核到的是：新驱动写的广播域表、每个口登记的广播域号、每个口的学习开关和隔离位图，读回来都和要求一致。两个口之间真的不直接转发，还没有测，要等能收发的那一步。

**现在的驱动写了什么**：
- 所有口登记进同一个广播域，0 号（`qca_ppe_main.c` 第 1621 行的 `ppe_vsi_init`，和 `qca_ppe_setup`）。
- 0 号广播域的成员是全部口加 CPU，开着地址学习。
- 每个口自己也开着学习，隔离位图写成"全部口"。厂商的代码里，这个位图里一位是 1 表示"可以转发到那个口"（`qca-ssdk` 的 `src/adpt/hppe/adpt_hppe_portvlan.c` 第 1798 行）。
- 地址表的一项里带着广播域的号（`qca_ppe_main.c` 第 241 到 254 行）。

推论：一号口上的主机发过报文以后，PPE 在 0 号广播域里记住了它的地址。二号口再来一个发给这个地址的报文，PPE 在同一个广播域里查到了，就直接从一号口发出去，不送 CPU。

**IPQ9574 的办法这块芯片用不了**：IPQ9574 的驱动靠一个寄存器位"口没有登记广播域时，报文送 CPU"（`ppe_config.c` 第 1947 到 1966 行）。厂商的代码里，这个位只在 IPQ9574 那一代的目录里有（`qca-ssdk` 的 `include/hsl/appe/`），这块芯片的目录（`include/hsl/hppe/`）里没有。

**厂商在这块芯片上的办法**：每个口一个自己的广播域（`qca-ssdk` 的 `src/ref/ref_vsi.c` 第 27 行和第 559 到 587 行）。每个广播域里，不认识的单播、组播、广播都只送 CPU（第 38 到 41 行）。

**新驱动的候选做法**（`ppe_config_isolation`）：
- 32 个广播域全部写成：不认识的单播、组播、广播只送 CPU；不开学习。
- 口 N 登记进它自己的广播域，这个广播域的成员是口 N 加 CPU。
- 每个口自己的学习也关掉。
- 地址表照现在的驱动清空一次。

推论：没有学习，地址表一直是空的，每个单播都算"不认识"，只送 CPU。就算以后表里有了东西，各个口也不在同一个广播域里，互相查不到。
以后把两个口放进同一个桥，就是把它们挪进同一个广播域。这是阶段 3 的事，这里不做。

**上机怎样看**：
- 第一步能看的：把广播域的表、每个口登记的广播域号、每个口的学习开关读回来，和写进去的值对一遍。
- 第一步看不了的：两个口之间真的不直接转发。这要等能收发的那一步，在两个口上各接一台机器来测。

### 4.2　查清的第二处：PPE 的队列怎样对应到 EDMA 的收包环

**结论**：有两张表，管的事不一样。真正决定"哪条队列的报文进哪个收包环"的是 EDMA 那一张，而 EDMA 那一张现在只把 0 号队列指给了主机的环。PPE 那一张现在的内容里没有主机用的环。

**第一张，在 EDMA 里**（`qca_edma.h` 第 130 行，队列号到环号的表）：
- 厂商的 EDMA 驱动在写这张表的地方有注释（`qca-nss-dp` 的 `hal/dp_ops/edma_dp/edma_v1/edma_cfg.c` 第 848 到 858 行）："开机时只用 0 号队列，指给主机的环；固件起来以后按需要改写。每一项装 8 条队列。"
- 现在的驱动和厂商一样，只写第 0 项，值是主机的收包环号 15（`qca_edma.c` 第 924 行）。
- 推论：第 0 项里，0 号队列指向 15 号环，1 到 7 号队列指向 0 号环。
- 这张表一共 64 项（厂商的 `edma_regs.h` 第 376 行）。第 1 到 63 项没有人写。上机（E-0001）：这 63 项不是 0，也不是固定的值。同一次引导里把驱动卸载再加载（EDMA 复位一次），它们不变；换一次引导，每一项都有几位不一样。也就是说它们是没有初始化过的内存里剩下的东西，8 号以后的队列进哪个环是不定的。
- 你定的：这些杂乱数值到第三步（收发）再处理。
- 0 号环现在的驱动没有打开。所以报文只要进了 0 号以外的队列，主机就收不到（推论）。

**第二张，在 PPE 里**（`qca_ppe.h` 第 321 行，每个环一行，写着"哪些队列归这个环"）：
- IPQ9574 的补丁在用到这张表的地方，都把它叫作"反压的配置"（0333 号补丁第 462、504、546 行的报错和调试信息）。推论：它的用处是环满了的时候，让 PPE 知道该停哪些队列，不是决定报文进哪个环。
- IPQ9574 的驱动把两张表写成一致的。
- 现在的驱动写的是 0、1、2、3 号环各对应哪些队列（`qca_ppe_scheduler.c` 第 720 到 739 行），主机用的 15 号环没有写。
- 这四行的来历查到了，是厂商的 `qca-ssdk` 写的（`src/init/ssdk_hppe.c` 第 1235 到 1245 行）：0 号环对应队列 0 到 3，3 号环对应队列 4 到 7，1 号环对应队列 8 到 11，2 号环对应队列 128 到 143。厂商是把一行十个字从头到尾连着写的（`src/hsl/hppe/hppe_reg_access.c` 第 57 到 64 行）。厂商在这块芯片上没有写 15 号环那一行。
- 这四行和第五节第 10 条里固件运行时"队列到环"那张表对得上：队列 1 到 3 进环 0，4 到 7 进环 3，8 到 11 进环 1，128 到 143 进环 2。不一样的只有 0 号队列：固件运行时它进 15 号环，而在 PPE 这张表里它记在 0 号环那一行。新驱动另外又把它记在了 15 号环那一行。
- 现在的驱动 2 号环那一行的写法是错的：先把十个字都写成 0，再单独补写第 4 个字（`qca_ppe_scheduler.c` 第 737、738 行）。多个字的表项要整项连着写，写到最后一个字才提交（第五节第 2 条），单独补的字没有提交。上机（E-0001）：照这个写法，2 号环那一行读回来十个字全是 0；改成整行连着写以后，读回来和厂商的值一致。

**送 CPU 的报文进哪条队列**（`qca_ppe_scheduler.c` 第 456 行的 `ppe_qm_init`）：
- 队列号 = 起始队列号 + 优先级给的偏移 + 哈希给的偏移。
- 目的是 CPU 口的，起始队列号是 0（第 448、468 行）。
- CPU 口的优先级偏移全部写成了 0（第 472 到 496 行）。
- 哈希的偏移，现在的驱动只清了第 14、15 两组（第 499 到 502 行）。CPU 口用的是第 0 组，没有清。为什么只清这两组，源码里没有说。IPQ9574 的驱动把每个口的哈希偏移都清零（`ppe_config.c` 第 1777 到 1786 行）。
- 上机（E-0001）：哈希偏移表 16 组里，第 0 到 11 组复位以后全是 0；第 12、13 两组没有人写，里面几乎每一项都不是 0，而且每次引导不一样；第 14、15 两组是驱动清成 0 的。所以哈希不会把送 CPU 的报文分到别的队列。驱动写进"目的到队列"那张表里的分组号只有 0 到 8，用不到第 12、13 两组。
- 另有两类报文不按"目的口"查，按"CPU 代码"或"服务代码"查。现在的驱动只写了其中一部分。上机（E-0001）："CPU 代码"那一段没有写到的项复位以后都是 0，也就是都指向 0 号队列。

**新驱动的做法**：
- EDMA 那一张：照做，0 号队列指给主机的收包环（`edma_hw_config`）。
- PPE 那一张：你定的。上一轮的原话："0 到 3 号环的四行照现在的驱动原样写，不删；另外加上主机收包环那一行。这四行的来历没有查清，没有查清的不改。到阶段 2 读 NSS 的代码时再核这四行。"这一轮的原话："2 号环那一行要写对。先去厂商的代码里把 0、1、2、3 号环这四行的内容核一遍，新驱动和厂商一致。写法改成整行连着写。这是 OpenWrt 现在那个驱动的一处错，新驱动里改掉。旧驱动的文件不动。"
- 照这两条做成的样子：四行的内容和厂商一致（核过，本来就一致）；每一行都用 `ppe_ring_map_row_write` 把十个字整行连着写；主机收包环那一行写 0 号队列，和 EDMA 那一张一致。
- 哈希的偏移：照做，只清第 14、15 两组，不多清。

**上机怎样看**：
- 第一步能看的，都是读寄存器：
  - EDMA 那一张表，第 0 项以外各项复位以后的值。
  - 哈希偏移表第 0 组复位以后的值。要是不是 0，送 CPU 的报文就可能进别的队列，到收包那一步以前要回来处理这一项。
  - "CPU 代码"那一部分，没有写到的项复位以后的值。
  - PPE 那一张表里五行（0 到 3 号环和主机收包环），写进去以后能不能原样读回来。
- 第一步看不了的：送 CPU 的报文是不是真的都落在 0 号队列、都进了主机的环。这要等收包那一步。

读寄存器可以用内核自带的办法：寄存器映射在调试文件系统里有一个 `registers` 文件，OpenWrt 默认打开了调试文件系统（`target/linux/generic/config-6.18` 第 1379 行）。这样第一步不用为了读寄存器多写代码。上机（E-0001）用的就是这个文件，好用。读多个字的表项时，要从第 0 个字起整项连着读；单独读中间一个字，读到的是上一次读过的那一项的内容。

### 4.3　内部环回口

**你定的**：内部环回口只有 IPQ60xx 开，IPQ807x 不开。原话："内部环回口：只有 IPQ60xx 开，IPQ807x 不开。新驱动在 IPQ807x 上不再写那两个寄存器，也不再动 7 号口的发送开关。"
这一条取代上一轮定的"照做"。

**现在的驱动做了什么**（`qca_ppe_main.c` 第 1663 到 1669 行）：
- IPQ807x 上环回口是 7 号口，IPQ60xx 上是 6 号口（第 1867、1884 行）。
- 往"口号减一"那个 MAC 的位置写两个寄存器：速率的门限写 21，打开环回并剥掉校验码。
- 等 100 毫秒。
- 打开这个口的发送开关。
- 随后 `qca_ppe_setup` 里对每个口的循环（第 475 到 485 行）又把 7 号口的发送开关关掉了，因为那个循环对 0 到 7 号口都执行，只给 CPU 口留着发送开关。

**为什么 IPQ807x 不开**（在厂商的 `qca-ssdk` 里查到的，只查了和环回口有关的几处，没有通读）：
- 厂商只在 IPQ60xx 上开环回口。
  - 开环回口的函数只认 6 号口，别的口直接报参数错（`src/adpt/cppe/adpt_cppe_portctrl.c` 第 266 行起，第 275 到 277 行）。
  - 这个函数只在芯片是 IPQ60xx 那一代时才登记（`src/adpt/hppe/adpt_hppe_portctrl.c` 第 5023 到 5027 行）。
  - 初始化里调它的地方，也只在 IPQ60xx 那一代的条件下面（`src/init/ssdk_hppe.c` 第 219 到 228 行）。
- 环回口那两个寄存器的定义，只在 IPQ60xx 那一代的目录里有（`include/hsl/cppe/cppe_loopback_reg.h` 第 23、104 行）。IPQ807x 那一代的目录里没有。
- 厂商在 IPQ807x 上对 7 号口做的事：初始化时打开它的发送开关（`src/init/ssdk_hppe.c` 第 56 到 58 行），另外给它设了 VLAN 方面的角色。没有写环回的那两个寄存器。
- 现在的驱动在 IPQ807x 上，是把 IPQ60xx 的这一套写到了第 7 个 MAC 的位置（地址 0x1c00 和 0x1c0c）。
- 它是给什么用的：我没有找到一句说明。找到的只有一句注释"6 号口是 IPQ60xx 上的环回口"（`src/init/ssdk_hppe.c` 第 852 行）。

**新驱动现在怎样**：
- 删掉了 `ppe_config_loopback` 这个函数：不写那两个寄存器，不等 100 毫秒，不打开 7 号口的发送开关。芯片数据里"内部环回口是几号"那一项也跟着删了。
- 代码里在原来调用它的位置（`ppe_hw_config` 里，各口 MAC 的共同设置之后、生成树协议报文的规则之前）留了一段注释，写明为什么 IPQ807x 不开、以后做 IPQ60xx 时要在这里加回来。
- 一处要照实说：每个口默认值的那个循环（`ppe_config_ports`）照旧对 0 到 7 号口都写发送开关，7 号口写的是"关"。这个循环我没有改：你这一条说的是环回口那一套；这个循环是对照表里另外一行（"只有 CPU 口开发送开关"，照做）。厂商的头文件写着发送开关复位以后本来就是关着的（`include/hsl/hppe/hppe_fdb_reg.h` 第 660 到 662 行），所以这一次写不改变硬件的状态。

**以后做 IPQ60xx 时要加回来**：

- 做法照厂商：速率 14（单位是每秒百万个报文，`include/fal/fal_port_ctrl.h` 第 75 行），门限 = 300 ÷ 14，取整是 21（`include/adpt/cppe/adpt_cppe_portctrl.h` 第 40 行）；打开环回并剥掉校验码；等 100 毫秒；再打开这个口的发送开关。
- 这两个寄存器的名字（`PPE_LPBK_ENABLE`、`PPE_LPBK_PPS_CTRL`）还留在 `ppe_regs.h` 里。
- 到那时"每个口默认值的那个循环随后把环回口的发送开关关掉"这件事要一起处理，不然开了又被关掉。

**上一轮记的那个实验**：上一轮定的是"等能收发的那一步做完以后，再编一个不开环回口的临时镜像，看阶段 1 的收发有没有差别"，要回答的是"阶段 1 的流量用不用得到它"。现在新驱动本来就不开，所以第三步（收发）做成的那个镜像，就是"不开环回口"时的读数。

### 第一步上机时要看的东西，和看到的

看的结果都出自上机实验 E-0001（阶段 1 第一步：驱动加载、开机配置、注册网口）。读数只写在 `上机实验/E-0001/报告.md` 里，这里只写结论。
E-0001 上了两个镜像：一个是定下 2 号环和环回口这两处改动以前的代码编的，一个是改以后的代码编的。下面没有另外说明的，两个镜像结论相同。

1. 内核的启动记录里，这个驱动没有报错。
   结论：没有报错。
2. `ip link` 列出 `lan1`、`lan2`、`lan3`、`lan4`、`wan` 五个口，没有 `eth0`。
   结论：是这五个口，没有 `eth0`。
3. 五个口的 MAC 地址对。
   结论：五个口的地址都等于出厂数据分区里的 `ethaddr`，也就是板级文件指的那个地址。比的是指纹。这一次没有和旧镜像比：旧镜像的输出没有了，这棵代码树现在编不出旧驱动的镜像。
4. 4.1 里列的读回项。
   结论：广播域的表 32 项、七个口各自登记的广播域号、八个口的学习开关和隔离位图，都和要求一致。发送开关只有 CPU 口开着。
5. 4.2 里列的读回项。
   结论：
   - EDMA 那张表第 0 项是写进去的值。第 1 到 63 项是没有初始化过的内存里剩下的东西：同一次引导里不变，换一次引导每一项都有几位不一样。
   - 哈希偏移表第 0 组 256 项全是 0。整张表里只有没有人写的第 12、13 两组不是 0，每次引导不一样。
   - "CPU 代码"那一段 256 项全是 0。
   - PPE 那张表：0、1、3 号环和主机收包环这四行对。2 号环那一行，改以前读回来十个字全是 0；改成整行连着写以后，和厂商的值一致。没有人写的 4 到 14 号环全是 0。
6. 环回口的两个寄存器、7 号口的发送开关、生成树协议报文的那条规则。
   结论：两个寄存器改以前（驱动写了它们）和改以后（驱动不写）读回来都是 0，所以读数分不出写没写；7 号口的发送开关两次都是关着的；生成树协议报文的那条规则和写进去的一样。
7. 1 号口在这块板子上没有接东西，它的时钟没有人开。看 PPE 的复位和上面各项读回有没有因此不正常。
   结论：1 号口的三个时钟确实没有开（硬件上也是关着的），2 到 6 号口的开着。上面各项没有因此不正常。另外单独读了一次 1 号口自己的 MAC 寄存器（两个寄存器各读一次）：读得出数，路由器没有重启，内核记录里没有新的错误。
8. 卸载再加载一次驱动，不报错，五个口还在。
   结论：卸载和加载都没有报错，五个口先没有后回来，地址的指纹没变，驱动写的每一张表和第一次加载以后一样。
9. 每个口的控制寄存器第 17 位。
   结论：八个口都是 1。它是厂商叫 `PROMISC_EN` 的那一位，复位以后就是 1，厂商开机时也把每个口写成 1，新驱动不去动它。该是 1。它是 0 时哪些帧会被丢，要等能收发以后才测得了。

**E-0001 另外读到的三处不对劲**（这三处这一轮都没有改，因为你定要改的只有两处）：
- **最大帧长表只有 0 号口写进去了。** 1 到 7 号口读回来还是复位以后的值：收发的最大帧长是 1514 而不是要写的 1522，PPE 一侧的两个计数器没有打开。原因（推论，有一步读数支持）：这张表每项两个字，新驱动先写第一个字，后来对第二个字做"读出、改两位、写回"；单独读第二个字读到的是硬件里上一次留下的那一项（读数支持的是这一句），那两位已经是 1，内核见值没变就不写；最后一个字没有写，这一项就没有提交。新驱动这一段是照现在的驱动写的，现在的驱动是同样的次序。
- **"优先级先信哪一处"在 IPQ807x 上没有写到地方。** 新驱动写的地址（0xe004 起，每个口隔 0x10）写完读回来是 0。在厂商的头文件里，这个地址是一张丢包计数表的第二个字（`qca-ssdk` 的 `include/hsl/hppe/hppe_portctrl_reg.h` 第 879 到 883 行，`src/hsl/hppe/hppe_portctrl.c` 第 476 行）。IPQ807x 管"优先级先信哪一处"的是另一个寄存器（0x60900 起，每个口隔 0x10；`include/hsl/hppe/hppe_qos_reg.h` 第 1474 到 1477 行、第 1536 到 1549 行），位的排法也不一样；它读回来八个口都是厂商头文件写的复位以后的值（第 1479 行），没有人写过它。新驱动用的位的排法，是厂商头文件里 IPQ60xx 那一代"最大帧长表"第二个字的排法（`hppe_portctrl_reg.h` 第 690 到 707 行）。新驱动这一段也是照现在的驱动写的（`qca_ppe_scheduler.c` 第 741 到 757 行）。
- **`br-lan` 不是这个驱动的口。** 它是 OpenWrt 的网络配置建的桥，成员是 `lan1` 到 `lan4`。读网口的那一刻它在不在，只看网络配置做到了哪一步。

## 五、已知的硬件事实

这一节的每一条都是你给的，出处都是"用户给的，以前在硬件上直接测到"。条件照你写的记。
这些都是在别的开机配置下测到的；用到哪一条时，新驱动写的值不一样就要重新核。

1. EDMA 的中断号补全了，这四个都是测到的：接收描述环 2 是 SPI 374，接收填充环 2 是 SPI 358，接收填充环 0 是 SPI 360，杂项是 SPI 344。
2. PPE 里多个字的表项：要整项连着写，中间不能读；写到最后一个字才真正提交；中途读第 0 个字，会取回表里的旧值，丢掉还没提交的第 0 个字。
3. 一个口不登记任何广播域时，从这个口进来的帧被芯片丢掉，到不了 CPU，也不泛洪。登记一个自己的广播域以后，帧到 CPU，不漏到别的口。
4. 每个口的隔离位图硬件照着做：清掉对方那一位以后，认识的单播和泛洪的帧都不再发给对方，发给 CPU 的帧照常。
5. 一个接收填充环用空了，所有接收环都停，补上缓冲以后一秒内恢复。这一条是固件运行时测的。
6. 接收缓冲比帧短时，硬件把一帧拆进两个相邻的描述符，第一个的状态字第 30 位是 1。
7. 发送前置头里编号为 4 的那个字（从 0 数起）：
   - 第 30 位置 1，帧不出口，被芯片丢掉；
   - 第 2 位置 1 的那一次，控制通道断了，原因没有查清；
   - 第 24、25 位管内层的 8100 标签，第 26、27 位管外层的 88a8 标签，值是 1 或 2 时硬件加标签，是 0 或 3 时不加。
8. 接收描述符的状态字：第 15 位表示 IP 头校验正确，第 14 位表示 UDP 校验正确；校验错的帧照样交给主机。发送这一边硬件不替主机补校验和。发送前置头不能指定帧进 PPE 的哪条队列。
9. 几个接收环可以同时收，芯片按哈希把同一条流固定分到一个环。每个口用自己的一对发送环也行，两个口同时满速互不影响。这一条是固件运行时测的。
10. 固件运行时各个环的归属：
    - 发送环：主机用 23，固件配了 0 到 7，8 到 22 空着；
    - 发送完成环：主机用 7，固件配了 0、2，1、3、4、5、6 空着；
    - 接收环：主机用 15，固件配了 0 到 3，4 到 14 空着；
    - 接收填充环：主机用 7，固件配了 0、2，1、3、4、5、6 空着。

    固件运行时"队列到环"那张表的内容：队列 0 进环 15，队列 1 到 3 进环 0，队列 4 到 7 进环 3，队列 8 到 11 进环 1，队列 128 到 143 进环 2，其余进环 0。
