# E-0001　阶段 1 第一步：驱动加载、开机配置、注册网口

这个实验在两个镜像上读同一套东西：一个是改以前的代码编的，一个是改以后的代码编的。读数脚本是同一个文件夹里的 `E-0001.py`，两个镜像跑的是同一个脚本。
留下来的是这份报告和这个文件夹里的两份结果摘要（`结果-改以前.json`、`结果-改以后.json`）。每一步的原始输出只在上机期间放在主机上，没有保留。
地址（MAC）的数值不写进任何文件，比地址只比指纹（md5 的前 12 位）。

用到的几个词：
- 新驱动：`ipq807x-eth`，在代码树 `worktrees/openwrt-nss-adaptation-workrepo` 的 `target/linux/qualcommax/files/drivers/net/ethernet/qualcomm/ipq807x/` 下面。
- 旧驱动：同一个 `qualcomm/` 目录里的 `qca_ppe_main.c`、`qca_ppe_scheduler.c`、`qca_edma.c`。

## 1. 问题、依据和判据

### 1.1 设计里哪件事要靠这个实验

第一步做完的样子是"驱动加载不出错，`ip link` 里列出每个口"。这句话本身要在路由器上看。

第一步还往硬件里写了一整套开机配置。后面第二步（连线）和第三步（收发）都建在这套配置上。这套配置里有几件事只读源码定不下来，要在硬件上读回来：

- 每个口是不是真的各在自己的广播域里。读不回来，第三步收到的报文不对时，分不清是收发的代码错了，还是口之间在硬件里串了。
- PPE 里"哪个环对应哪些队列"那张表，2 号环那一行要写对、和厂商一致。写没写进去，只有读回来才知道。
- EDMA 里"哪条队列进哪个环"那张表，只有第 0 项有人写。别的项是什么，决定第三步要不要自己把它们写上。
- 环回口：你定了 IPQ807x 不开。改以前、改以后硬件上各是什么样，要读。
- 口的控制寄存器第 17 位是 1，要弄清它是什么、该不该是 1。
- 改以后，除了定要改的两处，别的配置不能跟着变。

不做这个实验，第三步出了问题时没有一份"开机配置是对的"的底子可以排除。

### 1.4 口的控制寄存器第 17 位是什么，该不该是 1

读源码读出来的：
- 厂商的头文件把这一位叫 `PROMISC_EN`，复位以后是 1（`include/hsl/hppe/hppe_fdb_reg.h` 第 663 到 667 行）。整个寄存器复位以后是 0x2ff09（第 632 行）。
- 厂商开机时对 0 到 7 号口每个口都把它写成 1（`src/init/ssdk_hppe.c` 第 62 行）。写的就是这个寄存器的这一位（`src/adpt/hppe/adpt_hppe_portctrl.c` 第 3197 到 3221 行）。
- 厂商给 PPE 丢包原因起的名字里有一项叫 "Promisc drop"（`src/adpt/hppe/adpt_hppe_misc.c` 第 366 行）。
- 已经进 Linux 的 IPQ9574 驱动只定义了这个寄存器的第 0、3、16 位（`ppe_regs.h` 第 154 到 156 行），从来不动第 17 位。
- 新驱动和旧驱动都不写这一位：它们改这个寄存器时只改第 0、3、8 到 15、16 位（`ppe_config.c` 第 700 到 705 行，`qca_ppe_main.c` 第 479 到 484 行）。

推论：这一位是"这个口收不收目的地址不是给它的帧"的开关，是 1 时都收，是 0 时芯片会把一部分帧按 "Promisc drop" 丢掉。哪一部分帧，源码里没有说明。

该不该是 1：该是 1。依据是三条：阶段 1 要的是每个口的帧都送 CPU，多一种丢帧就和这个要求相反；厂商每个口都写成 1；它复位以后本来就是 1，新驱动不去动它。

这个实验能核的只是"它读回来是不是 1"。"写成 0 以后哪些帧被丢"在第一步测不了：新驱动还不能收发，没有帧进得了 PPE。

### 1.7 读没开时钟的 1 号口

1 号口的时钟关着。时钟关着的东西去读，可能把路由器读死，所以这一项单独用一次引导，只读它自己的 MAC 寄存器。

为什么要知道：这个驱动的寄存器映射对整个地址范围都开放。以后驱动里的代码，或者有人读调试文件，都可能碰到没开时钟的口的寄存器。读了会怎样，决定驱动要不要把这些地址挡住。

前提：路由器的看门狗在跑（读死了 30 秒以内会自己重启）；1 号口 MAC 时钟的打开次数是 0。前提不成立就不读。

读地址 0x1000 和 0x1018 各一次。三种结果都是答案：
- 读回来了数：记下读到的数，再核启动号没变、内核记录里没有新的严重错误。
- 命令没有回来，随后控制台出现启动的输出：路由器重启了。
- 命令没有回来，150 秒里控制台也没有启动的输出：路由器停住了。

### 1.8 最大帧长表为什么只有 0 号口那一项是对的

最大帧长表（判据"附带"）读回来只有 0 号口那一项是对的，1 到 7 号口那七项不对。照守则"附带读到的怪现象也要查清是哪一处"，加了一步读数来核下面这个解释。这一步是读到这张表不对以后加的，是我自己加的；它的判读在读以前写下。

解释（推论，读新驱动写这张表的代码读出来的）：
- 这张表每项两个字。新驱动对每个口先写第一个字（`ppe_config.c` 第 688 到 691 行），隔了几个别的寄存器以后，再"读出第二个字、改两位、写回去"（第 708 到 713 行）。
- 单独读第二个字，读到的不是这一项的，而是硬件里上一次留下的那一项的。写完 0 号口以后，留下的第二个字里那两位已经是 1。
- 内核的"读出、改、写回"在改完的值和读到的值一样时不写（内核 `drivers/base/regmap/regmap.c` 第 3274、3275 行）。所以 1 到 7 号口的第二个字没有写。
- 照你给的硬件事实，写到最后一个字才真正提交。最后一个字没有写，前面写的第一个字也就没有提交。

加的一步读数：先整项读 0 号口那一项，紧接着单独读 1 号口那一项的第二个字。判读：
- 单独读到的数等于 0 号口那一项的第二个字，而不等于整项读 1 号口时读到的第二个字：解释里"单独读第二个字读到的是上一项的"这一句成立。
- 单独读到的数等于整项读 1 号口时读到的第二个字：解释不成立，原因另查。
- 0 号口和 1 号口两项的第二个字本来就一样：这一步分不出来，另想办法。

## 2. 设置

### 2.1 两个镜像

### 2.2 怎样核路由器上跑的就是要测的镜像

- `boot-ram.py`（内存引导的脚本）的结果里：路由器取走的字节数等于镜像的大小；引导以后根文件系统是内存里的（tmpfs）；启动号和引导以前不同。
- `E-0001.py` 每次读数的第一步，读路由器上 `ipq807x-eth.ko` 的校验值，和主机上编出来的那个模块比。每一次引导都一致。

### 2.3 路由器和主机怎样接

- 串口：主机的 `/dev/ttyUSB0`，115200。所有读数都走串口。这两个镜像的网口还不能收发，ssh 用不了。
- 主机的 USB 网卡 `enxd4a2cde31c38` 接路由器的 `lan3`，只用来给 U-Boot 送镜像（TFTP，主机一侧的地址 192.168.11.10/24，由 `test-network.py` 加上和去掉）。
- 主机的 `eno2` 接路由器的 `lan2`，这个实验没有用它。
- `eno1`、`br-lan`（主机的上联）和 `enx224d686d5002` 没有碰。
- 路由器只做内存引导，没有往它的存储写任何东西。脚本读过一次出厂数据分区（只读的设备节点 `/dev/mtd14ro`），为的是算 `ethaddr` 的指纹。

## 3. 执行

### 3.1 在哪几次引导上读

- 每条判据：改以前、改以后的镜像各引导一次，各读一遍。读数在 `结果-改以前.json` 和 `结果-改以后.json` 里。
- 第 10 条要比几次引导：除了上面两次，改以前、改以后的镜像各另外引导一次，把"EDMA 队列到环"整表读回、逐行核过地址；还用了上机开始时路由器上已经跑着的那一次引导（镜像和改以前是同一份代码编的）。一共五次引导。这三次另外的引导也读了"哈希偏移全表"的摘要值（第 4.3 节）。
- 查清第 11 条多出来的那一处：在改以后的镜像（结果摘要的那一次引导）和改以前的镜像（单为这一项的一次引导）上各读了一遍哈希偏移全表的分组读数；在改以后的镜像上读了路由器的系统配置里 `br-lan` 那一项。
- 读没开时钟的 1 号口（第 1.7 节）：改以后的镜像，单独一次引导。

这几次引导之间路由器都没有断电。

### 3.2 实际跑的命令

引导（每次都一样，只有镜像和输出的文件夹不同）：

```text
sudo python3 脚本/boot-ram.py --image <镜像> --interface enxd4a2cde31c38 \
    --start reboot --serial /dev/ttyUSB0 --timeout 300 --output <输出的文件夹>
```

第一次引导时，等 `boot-ram.py` 打印出 `tftp_ready` 以后，加上 TFTP 的地址；这个地址一直留到全部做完才去掉：

```text
sudo python3 脚本/test-network.py apply --state <主机网络的状态文件> \
    --left-interface enxd4a2cde31c38 --left-address 192.168.11.10/24
```

每条判据的读数和两个镜像的比较：

```text
python3 E-0001.py --label 改以前 --module <改以前的模块> --output <输出的文件夹> --summary 结果-改以前.json
python3 E-0001.py --label 改以后 --module <改以后的模块> --output <输出的文件夹> --summary 结果-改以后.json
python3 E-0001.py --compare 结果-改以前.json 结果-改以后.json
```

哈希偏移全表的分组读数和 `br-lan` 那一项（`--extra`），读没开时钟的 1 号口（`--unclocked-read`）：

```text
python3 E-0001.py --extra --output <输出的文件夹>
python3 E-0001.py --unclocked-read --output <输出的文件夹>
```

`E-0001.py` 一次读数做的事，依次是：核模块；把控制台显示内核记录的级别调到最低；把全部东西读一遍（第一次加载以后）；`rmmod ipq807x-eth`；看网口；`modprobe ipq807x-eth`；把全部东西再读一遍（卸载再加载以后）；恢复控制台的级别；照判据比对；写摘要。
- 调控制台的级别只管控制台上显示什么；内核记录本身照常记，判据第 1 条照常读得到。
- 摘要值读回来不是 32 位十六进制数的，这一遍读数整个不用。

### 3.3 不是经 `E-0001.py` 发的命令

这些经 `脚本/serial-command.py` 各发了一次，都只读不改：
- 开工核对：启动号、内核版本、网口的名字、开机多少秒；路由器上有哪些工具；口时钟的名字、看门狗的状态。
- 读没开时钟的 1 号口以前：等到开机满 50 秒（等内核开机晚期的记录打完），读模块的校验值和网口的名字。
- 收工核对：1、2 号口六个时钟在硬件上开没开；启动号、模块的校验值、根文件系统、控制台的级别。

`boot-ram.py` 存下的引导串口记录里带着地址样式的字，每次引导以后都换成了 `xx:xx:xx:xx:xx:xx`，换完核过是 0 行。`E-0001.py` 的输出也核过，没有地址样式的字。

## 6. 没有查清的和异常

### 6.1 最大帧长表只有 0 号口写进去了（判据"附带"，两个镜像都是）

读到的：0 号口那一项是要写的值（收发的最大帧长 1522，两个计数器开着）。1 到 7 号口那七项是 05ea05ea、00000000：收发的最大帧长是 1514，两个计数器没有开。没有人写的时候它就是这个值。

是哪一处：`ppe_config.c` 里 `ppe_config_ports` 对这张表的写法。第 1.8 节里的解释有三句，核到的程度不一样：
- "单独读第二个字，读到的是硬件里上一次留下的那一项的"：第 4.4 节的读数直接支持。单独读 1 号口的第二个字读到 00000003，这是刚读过的 0 号口那一项的；整项读 1 号口读到的是 00000000。
- "内核的'读出、改、写回'在值没变时不写"：读内核源码读出来的（`drivers/base/regmap/regmap.c` 第 3274、3275 行）。
- "最后一个字没有写，第一个字也没有提交"：出自你给的硬件事实，读数和它一致。
- 这三句合起来说得通全部读数，但"1 到 7 号口的第二个字确实没有被写"这件事本身没有直接看到，是推论。

旧驱动对这张表是同样的次序（`qca_ppe_main.c` 第 459 到 463 行写第一个字；第 487 行调 `ppe_port_cnt_enable`，它在第 161 到 165 行对第二个字做"读出、改两位、写回"），所以旧驱动上多半也是这样。这一句是推论，没有在旧驱动上读过。

影响：1 到 7 号口收发的最大帧长留在 1514，不是要写的 1522（1514 加两层 VLAN 标签）；PPE 一侧这七个口的收发计数器没有打开。带 VLAN 标签的满长帧会不会因此被芯片丢掉，是风险，没有测，要等能收发。这两个镜像里这一处都没有改。

### 6.2 "优先级先信哪一处"在 IPQ807x 上写到了别的表

读到的：新驱动的 `ppe_config_qos` 写的地址（0xe004 起，每个口隔 0x10）写完读回来全是 0。

是哪一处：在厂商的头文件里，0xe000 起是一张丢包计数表，每项三个字（`include/hsl/hppe/hppe_portctrl_reg.h` 第 879 到 883 行、第 897 到 905 行；`src/hsl/hppe/hppe_portctrl.c` 第 476 行）。新驱动写的是它每一项的第二个字。IPQ807x 管"优先级先信哪一处"的是另一个寄存器，在 0x60900 起，每个口隔 0x10（`include/hsl/hppe/hppe_qos_reg.h` 第 1474 到 1477 行、第 1536 到 1549 行），位的排法也不同；它读回来八个口都是 00023440，正是厂商头文件写的复位以后的值（第 1479 行）。新驱动用的位的排法，是厂商头文件里 IPQ60xx 那一代最大帧长表第二个字的排法（`hppe_portctrl_reg.h` 第 690 到 707 行）。

新驱动这一段是照旧驱动写的（`qca_ppe_scheduler.c` 第 741 到 757 行）。

影响：IPQ807x 上"优先级先信哪一处"实际是硬件复位以后的值。阶段 1 送 CPU 的报文优先级偏移全是 0，都进 0 号队列，所以阶段 1 看不出差别（推论）。这两个镜像里这一处都没有改。

### 6.3 环回口的两个寄存器读不出"写了"还是"没写"

改以前驱动往地址 0x1c00 写了 9、往 0x1c0c 写了 21，读回来都是 0；改以后驱动不写，读回来也都是 0。所以这两个地址在 IPQ807x 上写了留不下读得到的东西。证明"改以后不写"的是代码和模块（第 2.1 节），不是读数。这两个地址在 IPQ807x 上到底是什么，没有查清：厂商在 IPQ807x 那一代的头文件里没有定义它们。

### 6.4 没有人写的两处内存，每次引导不一样

- EDMA 队列到环的表第 1 到 63 项（第 4.2 节）。
- 哈希偏移表第 12、13 两组（第 4.3 节）。

这两处在同一次引导里都不变，换一次引导就变，每次有一部分位不同。它们是没有初始化过的内存里剩下的东西（推论，依据就是上面这个变法）。这几次引导之间路由器都没有断电，断电以后是什么样没有读过。

### 6.5 `br-lan`

`br-lan` 在网口的名单里时有时无：改以前的镜像第一遍读的时候没有它，改以后的镜像有；每次卸载以后它还在，加载以后那一遍读的时候又没有。它是 OpenWrt 的网络配置建的桥（读过它的名字、种类和成员，第 4.3 节），不是这个驱动注册的口。读的那一刻它在不在，看网络配置当时做到了哪一步（这半句是推论）。判据第 2 条和第 8 条只看五个口和 `eth0`，不受它影响。

### 6.6 没有核到的

- 绑定说明文件没有用 Linux 的绑定检查工具核过：主机上没有这个工具，没有授权安装。只核了它是合法的 YAML、例子里中断和名字的个数对得上。
- 读没开时钟的 1 号口，只读了两个寄存器各一次；1 号口 MAC 别的寄存器、万兆 MAC 的寄存器没有读。
- 两个口之间真的不直接转发、送 CPU 的报文真的都进 0 号队列和主机的环：第一步测不了，要等能收发的那一步。
